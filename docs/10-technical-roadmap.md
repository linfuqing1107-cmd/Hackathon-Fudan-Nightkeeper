# Nightkeeper 整体技术路线说明

版本：v0.2说明稿  
日期：2026-09-12  
适用对象：项目团队、比赛评委、临床合作方与后续技术接入方  
项目定位：精神卫生院外随访与个体变化核实工作台

## 1. 执行摘要

Nightkeeper将穿戴观测、患者简短自报和服药反馈整理为可追溯的信息，利用确定性规则发现需要核实的变化，再由医护完成联系、判断与记录。大模型作为信息整理助手，不参与自动诊断、临床风险定级或用药决策。

整体路线为：

**先做可运行、可解释的随访闭环，再接真实设备；在取得合规纵向数据与独立临床结局后，开展预测模型研究。**

当前仓库已有v0.2本地演示代码，采用Next.js、TypeScript、PGlite、同步规则及模板摘要。PostgreSQL独立服务、后台Worker、真实设备和外部大模型均属于后续建设内容。本说明依据当前源码、依赖声明与实现状态文档整理，本轮未重新运行应用测试，不代表生产验收或临床验证。

## 2. 产品边界与使用场景

### 2.1 服务对象

- 患者：完成短问卷、反馈服药情况、查看授权状态和提出联系请求。
- 医护：查看所分配患者的变化、核实依据、处理随访任务并记录结果。
- 管理员：操作当前演示空间、重置合成数据及模拟同步恢复，不默认读取临床正文。

### 2.2 首版演示

| 案例 | 数据表现 | 应展示的系统行为 |
| --- | --- | --- |
| 平稳 | 睡眠、精力和服药反馈平稳 | 不产生额外核实任务 |
| 多维变化 | 持续睡眠减少、精力自报增加，另有未服药自报 | 分别形成变化核实与服药核实任务，给出具体证据 |
| 设备掉线 | 穿戴数据中断，自报仍存在 | 形成数据质量任务，趋势留空，不把缺失当作低活动 |

首版仅使用合成患者与数据。设备阈值和规则参数只用于演示，不得直接用于真实患者。系统不承担急救服务，不承诺预测复发或降低再住院率。

## 3. 总体架构

### 3.1 当前实现：单进程本地原型

```text
医护浏览器 / 患者手机网页 / 管理页面
                      |
           Next.js + React + TypeScript
                      |
       同源API：会话、范围授权、参数校验
                      |
      领域服务：报告、规则、任务、审计、模板摘要
                      |
         PGlite事务与本地持久化
     空间状态JSONB + 任务约束 + 幂等缓存

数据来源：固定合成场景、患者演示反馈、管理员模拟恢复
```

数据写入与规则执行目前同步完成。每个浏览器演示空间拥有独立领域状态。当前版本只面向回环地址运行，不应直接通过反向代理发布到公网。

### 3.2 目标架构：模块化单体与后台任务

```text
真实设备适配器 / 患者反馈
            |
      授权与Schema校验
            |
 PostgreSQL：标准观测、报告、任务、审计、持久Job
            |
  Worker：质量检查、基线计算、规则评估
            |
       人工核实任务
            |
医护工作台：认领、联系、记录、回访、关闭
            |
   可选摘要服务：模板 / 大模型草稿
```

后续保留单体业务边界，通过Worker隔离耗时任务，不为了比赛原型引入微服务、Redis或复杂消息中间件。具体扩容选择依据负载测试，而非预先增加基础设施。

## 4. 技术栈与选型理由

| 层级 | 当前实现或声明 | 目标与选择理由 |
| --- | --- | --- |
| 语言 | TypeScript | 前后端共享类型，减少字段口径漂移 |
| 页面与接口 | Next.js 16.3.5；React依赖声明为19.2系列 | 同源页面与API，减少跨服务与跨域复杂度 |
| UI | Recharts、Lucide React | 趋势可视化与统一图标，服务密集工作台而非营销页面 |
| 参数校验 | Zod | 将请求验证集中管理；类型检查不能代替运行时校验 |
| 持久化 | PGlite 0.5.8 | 无需Docker即可运行本地演示；不作为多进程生产数据库方案 |
| 目标数据库 | 独立PostgreSQL与关系化迁移，未实现 | 提供并发、索引、约束、备份与独立运维能力 |
| 目标后台任务 | Node.js Worker与数据库Job，未实现 | 处理同步、重算和摘要，避免阻塞请求 |
| 验证工具 | Vitest、Playwright、TypeScript | 分别覆盖业务规则、浏览器流程及静态类型 |
| 依赖管理 | npm与package-lock.json | 用锁文件固定实际安装版本，升级需回归测试 |

技术版本来自仓库package.json；包含版本范围的依赖，以package-lock.json最终解析值为准。是否采用最新版本不是项目有效性的依据。

## 5. 数据路线

### 5.1 来源与最小字段

| 来源 | 规划字段 | 当前边界 |
| --- | --- | --- |
| 穿戴 | 睡眠起止、时长、步数、分时活动、夜间或静息心率 | 当前为固定模拟数据，未接厂商接口 |
| EMA | 情绪、精力、睡眠需求、主观困扰及未来病种相关问题 | 演示字段，临床措辞与量表适用性待审阅 |
| 服药反馈 | 已服、未服、不确定、未服原因 | 主观反馈，不是实际摄入证明 |
| 随访 | 联系结果、核实原因、处置、下次联系时间 | 人工记录，不由模型自动决定 |
| 质量与来源 | 同步时间、有效性、设备版本、观测版本、覆盖率 | 当前睡眠质量实现较完整，其余需扩展 |

### 5.2 标准化处理

目标处理顺序：来源授权检查、格式校验、单位统一、时间分桶、去重、质量评估、指标计算、规则评估。

- 缺失与零分开存储，不以零补齐未佩戴或不同步的时段。
- 原始自报和修订版本保留，历史任务证据不被静默替换。
- 设备提供的睡眠时长和分期均视为算法结果，不称为真实睡眠测量。
- 夜间心率与静息心率保留来源定义，不直接混成一个指标。
- HRV未来接入时记录SDNN或RMSSD、窗口和设备；不同口径不直接合并。
- 当前中国时区固定；跨区旅行和夏令时不是已支持能力。

### 5.3 真实设备接入路线

定义统一适配器输出Observation，再逐厂商实现授权、同步、历史补传和撤回。优先接一个明确开放所需字段的设备生态，不以“App中能看到”推断第三方可以获取。

设备接入前需取得：官方授权条件、真实字段样例、采样/汇总粒度、延迟与补传说明、数据托管地点、费用、用户撤回路径。完成连续佩戴验证后，再决定是否扩展品牌。

## 6. 核心计算路线

### 6.1 质量检查先于变化判断

只有满足质量条件的记录才参与对应计算。数据不足时结论为不足，不判平稳。当前重点处理睡眠VALID/MISSING/PARTIAL；覆盖区间并集、活动分时与跨设备质量判断属于后续工作。

### 6.2 个人基线

当前实现冻结睡眠基线，与最近已结束日期的数据比较。目标设计按指标维护独立基线、参与数据和版本，避免将当前异常吸收进动态基线。

演示采用14日窗口及最低有效日参数，真实队列窗口需临床与统计方案另行确定。换设备或算法时需评估基线失效，不直接延续。

### 6.3 确定性规则

当前演示包括持续睡眠与精力变化、同步中断、连续未服药自报及独立主动请求。规则输出核实任务和证据，不输出疾病诊断。

同一输入、时间和规则版本应得到一致结果。规则与大模型解耦，修改参数必须增加版本并回归场景。当前只对最近结束日重算；任意历史窗口重算尚未实现。

### 6.4 人工处置

任务认领后进入核实，可安排回访、恢复处理或记录结果后关闭。重复变化不会反复建同类开放任务，数据恢复也不自动判定问题已解决。当前支持CLAIM、WAIT、RESUME、CLOSE；合并和转派尚未开放。

## 7. 大模型介入位置

### 7.1 当前与后续

当前摘要为确定性模板，明确标记TEMPLATE，不调用外部模型。后续优先新增一个“随访准备摘要”入口，汇总事实并生成待核实问题草稿，不将大模型接入全部功能。

| 能力 | 大模型是否必要 | 规划方式 |
| --- | --- | --- |
| 数据采集、去重、质量、基线 | 否 | 确定性程序 |
| 规则判断、权限与状态迁移 | 否 | 规则、数据库约束和服务端授权 |
| 近期事实摘要 | 可选 | 结构化事实输入，证据引用输出，人工确认 |
| 核实问题草稿 | 可选 | 只围绕观察事实提出非诱导性核实问题 |
| 医护记录整理 | 后续可选 | 整理既有记录，不补写未发生事实 |
| 指南检索、随访录音整理 | 后续研究 | 经审核知识库或授权录音，另定验证与隐私要求 |

### 7.2 目标调用链

```text
已有核实任务
   -> 后端提取最少必要事实并分配sourceId
   -> 模型生成“观察事实 / 待核实问题”结构化草稿
   -> 校验格式、引用归属和数值一致性
   -> 医护审阅
```

模型不直接查询全库、不调用任务修改工具、不自动向患者发诊疗内容。不返回诊断、复发概率或调药方案。格式和引用校验不能保证语义无误，因此人工审阅不可省略。

目标设计中无密钥、超时或非法输出均退回模板。当前未集成模型，这些降级和注入防护不能算已完成验证。真实数据外发须单独获批。

## 8. 存储、一致性与接口

### 8.1 当前数据模型

PGlite中workspaces.state以JSONB保存空间领域状态，sessions保存会话，idempotency保存写请求结果，task_constraints投影任务以约束同患者同类型开放任务唯一。

写操作在事务中锁定当前空间、检查幂等键、执行业务、更新状态和约束。同空间写入串行化，适合小规模本地演示，不代表已满足生产并发目标。同一数据目录只能由一个Node进程持有。

### 8.2 目标迁移

拆分Patient、Observation、DailyReport、MedicationReport、Baseline、Evaluation、Task、Followup、Consent与Audit等关系表，引入版本迁移、外键与索引、事务Job队列。迁移需验证数量、关联和任务证据一致，不能仅更换数据库连接字符串。

### 8.3 API

当前采用/api/v1，同源路由集中实现，/view返回角色过滤的演示快照。/api/v1/openapi基于请求schema生成，响应实体尚未完整描述。

目标补齐通用批量接入、分页、完整请求响应契约、历史窗口查询与异步Job状态。完整接口路线见[API契约](04-api-contract.md)，已实现差异见[实现状态](09-implementation-status.md)。

## 9. 安全与运行边界

当前代码包含会话、患者范围、Origin/CSRF检查及写操作幂等；这些是本地演示保护，不是生产认证或安全认证。公网运行前需重新评审登录、空间隔离、会话生命周期、HTTPS、分类限流与审计。

仓库不得包含医院附件、真实患者信息、设备账户或密钥。撤回采集与删除历史数据是不同操作，真实保留期限和备份删除流程须由机构确定。

主动请求不依赖基线，但当前仅生成演示任务，没有真实值班响应或外部通知。不得向用户暗示24小时有人接警。

## 10. 测试与验收路线

| 层级 | 核心检查 |
| --- | --- |
| 单元 | 基线边界、连续天数、缺失、规则参数、状态迁移 |
| 接口/数据库 | 越权、幂等冲突、事务回滚、报告修订、开放任务唯一 |
| 浏览器E2E | 三个案例、患者反馈、认领、回访、摘要审阅与关闭 |
| 视觉与可访问性 | 桌面和手机适配、趋势空缺、文字状态、键盘表单操作 |
| 未来性能与故障 | 多用户并发、独立Worker重试、数据库恢复、模型超时 |
| 未来临床 | 独立结局、前瞻性验证、误报负担、提前量和医护工作量 |

已有测试工具和CI配置不等于所有用例通过。本轮仅核对技术文档与源码状态；测试结果应由实际运行日志和持续集成结果提供。模型研究不得将同一自报既用作预测输入，又当作独立临床结局。

## 11. 分期开发规划

| 阶段 | 交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| 当前v0.2 | 本地合成案例、规则核实任务、双端网页、模板摘要 | 按测试计划完成回归和演示验收 |
| 工程增强 | 关系化存储、批量接口、历史重算、Worker、完整契约 | 幂等、故障恢复及并发测试达标 |
| 比赛公开演示 | 生产式认证、演示隔离、HTTPS、部署说明 | 权限、许可、评分要求明确，只使用合成数据 |
| 设备与AI增强 | 一个真实适配器；可选大模型摘要 | 分别取得数据许可和模型数据处理批准，完成专项验证 |
| 临床试点 | 指定病种、审阅问卷、人工响应SOP、真实随访 | 伦理、安全、临床及统计方案获批 |
| 后续研究 | HRV辅助、预测模型、跨中心验证及干预评价 | 足够纵向数据和独立结局，不用比赛演示效果替代证据 |

首版不要求向量数据库、知识图谱、多Agent编排或自训练大模型。后续只有明确问题和评估收益时再引入。

## 12. 对外说明口径

可使用：

> Nightkeeper采用模块化Web架构，将患者自报与穿戴观测转化为可解释的人工核实任务。当前已开发本地合成数据原型，后续按设备授权和临床验证逐步接入真实数据。大模型用于辅助整理随访信息，临床判断保留在医护端。

不可使用：“已接入真实穿戴”“AI已能预测复发”“已验证降低住院率”“已达到生产安全标准”。当前大模型仍未接入，对外应说明现有摘要是模板。
